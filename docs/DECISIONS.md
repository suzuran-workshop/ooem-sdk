# DECISIONS

## ADR-001：纯前端单页，不引入服务端

- 日期：2026-10-24
- 状态：已采纳
- 背景：需求是单机数独，不需要账号、排行榜或多人。
- 考虑过的方案：纯前端 SPA；带 Hono API + SQLite 的全栈骨架。
- 决策：采用纯前端 SPA，全部数据留在浏览器。
- 为什么选这个：功能闭合在客户端，零运维、零请求延迟，静态托管即可。
- 为什么不选其他：后端只会增加部署与数据合规成本，不带来当前价值。
- 后果：无跨设备同步；统计只对本浏览器有效。
- 何时重新审视：需要账号、云存档、排行榜或在线对战时。

## ADR-002：用 `@m3e/react` 提供组件，棋盘使用原生 CSS

- 日期：2026-10-24
- 状态：已采纳
- 背景：指定 UI 采用 `@m3e/react`；数独棋盘需要极高的布局与状态控制自由度。
- 考虑过的方案：全部使用 M3E 组件；M3E 组件 + 自定义棋盘；Tailwind/shadcn。
- 决策：按钮、弹窗、开关、主题、Snackbar 使用 M3E；棋盘与数字键盘内部布局使用 CSS 与 M3E 设计令牌。
- 为什么选这个：M3E 的交互组件能直接提供 Material 3 Expressive 的形态与动效；棋盘需要 9×9 精确网格、粗分隔线和逐格状态，用 Web Component 包裹反而增加复杂度。
- 为什么不选其他：Tailwind/shadcn 与指定 UI 栈冲突；纯 M3E 棋盘难以控制 81 格细节。
- 后果：自定义 CSS 需要跟随 `--md-sys-color-*` 令牌，避免写死主题色。
- 何时重新审视：M3E 提供成熟的棋盘/网格组件，或视觉规范改为其他设计系统时。

## ADR-003：客户端生成唯一解题目

- 日期：2026-10-24
- 状态：已采纳
- 背景：无后端，但题目不能出现多解或错误。
- 考虑过的方案：内置固定题库；运行时随机生成；请求外部题库。
- 决策：运行时用随机回溯 + 唯一解计数生成。
- 为什么选这个：每局不同，离线可用，避免题库体积与外部依赖。
- 为什么不选其他：固定题库重复率高；外部题库引入网络与版权依赖。
- 后果：生成逻辑需要测试覆盖；极端难度下提示数可能高于目标 1–2 格。
- 何时重新审视：需要人工精选题目、每日挑战或指定题型时。

## ADR-004：对局与统计使用 `localStorage`

- 日期：2026-10-24
- 状态：已采纳
- 背景：需要刷新/关闭后继续，且无账号。
- 考虑过的方案：只在内存；`localStorage`；IndexedDB；远端。
- 决策：使用带版本键的 `localStorage`，读取时做结构校验，失败则回退新局。
- 为什么选这个：数据量小、同步 API 简单，适合单局与少量统计。
- 为什么不选其他：IndexedDB 过重；远端需要后端。
- 后果：站点数据清理、隐私模式或无存储权限时无法持久化，但游戏仍可在内存中完成。
- 何时重新审视：需要大量历史对局或跨设备同步时。

## ADR-005：难度用目标提示数近似，并始终服从唯一解

- 日期：2026-10-24
- 状态：已采纳
- 背景：难度既要有区分度，又不能牺牲题目的唯一解。
- 考虑过的方案：严格按提示数；按求解技巧评分；只按目标提示数挖空后不校验。
- 决策：为四档设置目标提示数；挖空时逐次校验唯一解，允许最终提示数在目标附近浮动。
- 为什么选这个：实现简单、结果可靠，避免为了凑数生成多解题。
- 为什么不选其他：严格凑数可能生成多解；技巧评分成本高且不易验证。
- 后果：同难度题目在主观难度上可能略有差异。
- 何时重新审视：需要更精确的难度曲线或专业评级时。

## ADR-006：单页，不引入路由

- 日期：2026-10-24
- 状态：已采纳
- 背景：游戏所有界面都是同一棋盘上的弹窗。
- 考虑过的方案：React Router；HashRouter；不装路由。
- 决策：不装路由，用本地状态控制弹窗。
- 为什么选这个：没有真实页面切换，静态托管也不需要 `404.html` 回退。
- 为什么不选其他：路由只会增加依赖与部署配置。
- 后果：没有可分享的对局深链接。
- 何时重新审视：需要分享棋局、独立设置页或帮助页时。

## ADR-007：GitHub Pages 的 `base` 由 CI 注入

- 日期：2026-10-24
- 状态：已采纳
- 背景：项目页部署在 `/<repo>/` 下，本地开发在 `/`。
- 考虑过的方案：写死仓库名；运行时推断；CI 注入 `PAGES_BASE_PATH`。
- 决策：Vite 配置读取 `PAGES_BASE_PATH`，默认 `/`；HTML 使用 `%BASE_URL%`。
- 为什么选这个：代码不绑定仓库名，用户页/自定义域只需改变量。
- 为什么不选其他：写死仓库名会在迁移或改名时白屏。
- 后果：部署配置需要与仓库变量保持一致。
- 何时重新审视：迁移到其他静态托管平台时。

## ADR-008：统计入口只保留顶栏一个

- 日期：2026-10-24
- 状态：已采纳
- 背景：初版在顶栏、侧栏和主内容区同时提供统计入口，信息重复。
- 考虑过的方案：保留多处入口；只保留顶栏统计图标；只在设置中放统计。
- 决策：只保留顶栏统计图标，移除火焰连胜按钮、侧栏「已完成 x 局」与「查看统计」。
- 为什么选这个：统计是低频动作，单一入口更清晰，主内容区让位给棋盘与操作。
- 后果：连胜与完成局数只在统计弹窗中查看。
- 何时重新审视：需要在对局中实时展示连胜时。

## ADR-009：`vite-plugin-pwa` 负责离线缓存，「检查更新」做全量失效

- 日期：2026-10-24
- 状态：已采纳
- 背景：纯静态 SPA 希望首次打开后可离线、重复访问更快，同时要能主动拿到最新构建。
- 考虑过的方案：不缓存；手写 Service Worker；`vite-plugin-pwa`（Workbox generateSW）。
- 决策：接入 `vite-plugin-pwa`，`autoUpdate` 接管新版本并预缓存构建产物；「关于 → 检查更新」注销全部 Service Worker、清空 Cache Storage，然后重新载入。
- 为什么选这个：Workbox 自动处理哈希文件名与预缓存清单，配置少；全量失效不依赖插件内部版本号，行为可解释。
- 为什么不选其他：手写 SW 容易漏掉更新与清理；完全不缓存不满足离线诉求。
- 后果：只清离线缓存，不清 `localStorage`，重载后对局与统计仍在；首次访问完成后才具备离线能力。
- 何时重新审视：需要后台同步、推送或更细粒度的资源策略时。

## ADR-010：项目信息放在标题触发的「关于」弹窗

- 日期：2026-10-24
- 状态：已采纳
- 背景：需要展示提交号、仓库地址与手动更新入口，但主界面不增加常驻控件。
- 考虑过的方案：页脚常驻版本号；塞进设置弹窗；点击标题打开独立弹窗。
- 决策：标题文字改为按钮，点击打开「关于」弹窗；提交号在构建时注入（CI 用 `GITHUB_SHA`，本地用 `git rev-parse --short=7 HEAD`，无提交时显示 `dev`）。
- 为什么选这个：标题是天然的项目身份入口，不占用操作区，也不干扰对局。
- 为什么不选其他：页脚常驻稀释注意力；只读信息放进「设置」破坏语义。
- 后果：标题的可点击性需要视觉与焦点态提示；提交号只对构建产物准确。
- 何时重新审视：需要完整更新日志或版本对比时。
